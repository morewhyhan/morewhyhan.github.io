# 博客内容与发布规范

本文件是「虚船向远」仓库的工作规范，记录用户已确认的要求与当前实现。更新规则时先核对用户最新指示；不要把暂定分类、待建设功能或机器生成的目录误写成已确认事实。相关源码位于本仓库；知识体系的原规范位于同级目录 `../知识仓库研究/目录.md`，学习树及其边界见 `../知识仓库研究/学习目录/使用说明.md` 和 `主题层级说明.md`。

## 一、如何组织内容

### 学科目录

知识仓库的学科目录主要用于组织各领域的通识内容和学习路径，使用其学科名称和层级。博客只在实际有合适内容时建立相应入口；不能将整棵学习树机械复制到网站，也不要把一般随笔按出现的人物、词语或背景强行分到学科。学科内的学习主题与跨内容的专题是不同概念。

### 用户自己的专题与文章

用户的个人随笔作为自己的专题集中组织，目前路径是「专题 → 生活随笔 → 具体文章」。不要把七篇随笔分别拆到哲学、历史、社会学等学科。当前已有的 Freqtrade 教程在「专题 → 量化交易」；这是现有文章的具体放置，不意味着以后每篇文章都要按题材自动新建专题。

专题、系列和课程阅读目录是不同的组织方式。一个系列若需要像课程一样按顺序展开，应有自己的列表与可点击的讲次，但用户原创系列仍是用户自己的内容，不属于图书或其他人的课程。创建新专题或命名应结合用户意图与实际内容，不自行恢复已删除的专题。

文章正文只维护一份。目录、专题、搜索和其他关联入口指向原文，不复制正文制造多个来源。引用或关联应有内容依据；共同标签本身不证明因果关系。个人观点、引用和可以核实的事实应分清楚。

### 其他人的图书与课程

外部图书、课程和原文资料保留在独立的「图书笔记」入口；注明原作者、来源与内容性质。不得因路径展示类似就放进用户的原创专题，也不得把他人章节记为用户原创。课程按作品、分组、讲次组织，保留原顺序与原文链接。当前课程包括《决策算法100讲》和《姜学勤心理史学》。

首页、时间轴和文章统计中的课程入口是作品级入口；内部讲次是阅读页。统计和展示时要分清一篇个人文章、一套课程和一讲课程，不把课程讲次数伪装成原创文章数。

## 二、页面与逐级路径

文章、专题分类、课程目录、课程分组和讲次都要有清楚的可点击层级路径，当前页面标识为当前位置。例如：

```text
首页 → 分类 → 专题 → 生活随笔 → 某篇随笔
首页 → 图书笔记 → 姜学勤心理史学 → 伟大经典 → 某一讲
首页 → 图书笔记 → 决策算法100讲 → 某一讲
```

每个上级链接必须指向真实且正确的上级页面；不将课程挂进个人专题。列表应能进入文章或讲次，讲次应能返回目录，原有前后讲次导航保持可用。图书与课程保留作者和来源信息。新旧网址变更时检查站内引用及旧链接，必要时提供跳转。

网站以「分类」作为文章分类入口，不再单独设置内容目录；旧地址 `/content-directory/` 跳转至分类。仓库根目录的 `博客现有内容目录.md` 是本地 Markdown 目录。分类在文章 front matter 中维护。`source/js/content-breadcrumb.js` 当前包含手工维护的文章地址、分类和课程讲次标题映射；新增、移动、改名或删除内容时必须检查并更新该脚本及本地目录，不要认为新增文章会自动出现路径。`tools/jiang-xueqin-titles.mjs` 是课程分组及中文标题的既有数据，改动时要同步核对路径脚本。若以后实现自动生成，应以实际代码和构建结果验证后再更改这条说明。

`scripts/knowledge-graph.js` 生成 Hexo 图谱数据；`tools/sync-quartz-content.mjs` 从源码生成知识花园内容，`npm run build` 将 Quartz 挂载到 `/notes/`。Quartz 的生成目录会被重建，不能只在那里维护唯一原文。检查图谱、知识花园、搜索及首页和时间轴，使分类或内容变化不留下失效链接或错误来源。

## 三、文件与写作

- 自己的文章在 `source/_posts/`。标题、日期、分类等使用 front matter；分类按用户确定的实际专题填写。
- 外部资料目前在 `source/book/`，课程作品入口在 `source/_posts/`，不要将这种入口误认成原创文章。
- 机制卡片在 `source/knowledge/cards/`；是否公开、如何进入图谱按实际配置与内容核对。
- 网站配置在 `_config.yml` 与 `_config.butterfly.yml`，自定义样式和脚本在 `source/css/` 与 `source/js/`。尽量不要直接修改 Butterfly 主题子模块。
- 新增文章时同步更新根目录 Markdown、路径脚本及相关页面，检查分类和生成的实际 URL。暂时没有足够依据时，不猜测作者、来源或学科归属。
- 用户曾要求删除《大学生目标分析》和《给大学生》专题；不得从旧提交、草稿或备份恢复，除非用户再次明确要求。

## 四、源码分支与网站分支

经 2026-10-28 核对，GitHub 默认分支是 `source`，公开站点部署分支是 `gh-pages`，没有 `main` 分支。两者是不同内容，不要求文件逐个相同：

| 分支 | 内容 | 操作 |
| --- | --- | --- |
| `source` | 可编辑的文章、配置、脚本、规则与构建工具 | 在此提交并推送源码 |
| `gh-pages` | 根据对应源码构建出来的静态网站 | 用构建结果发布，不当作源码编辑，也不把 `source` 直接合并覆盖 |

“内部写作分支”指它的工作用途，不保证它是私密的。不得将密码、令牌或私密资料提交到任何远端分支。

### 正常同步流程

1. 检查 `git status`、当前分支与远端最新状态；保留无关的用户修改，只暂存本次工作文件。
2. 在 `source` 修改文章或规则并核对；按需要运行 `npm run build`，此命令生成 Hexo 和 Quartz 并运行现有验证。
3. 提交并推送 `source`；需要更新网站时，使用项目的 `npm run deploy` 或等效流程，把本次构建的 `public/` 发布到 `gh-pages`。部署仓库和目标分支应先核对，不能把源码直接推到展示分支。
4. 分别核对远端 `source` 的源码提交与 `gh-pages` 的发布提交；检查网站重要入口和链接。发布可能有延迟或网络访问失败，应如实报告是否实际验证线上页面。
5. 仅修改根目录规则文件时，它不进入 `public/`，因此展示分支无需包含这些规则；确认现有展示内容仍对应最近一次网站构建即可。不要为了让分支哈希一致而合并它们或制造无意义的部署。

当前机器曾使用 WSL Ubuntu 的 Git/SSH 推送，Windows 网络和线上访问可能失败；遵循实际可用的认证方式，不把密钥或凭据写入文档。

## 五、发布验收

- 原创随笔可从「专题 → 生活随笔」找到，文章页路径每一级可点击。
- 外部课程从自己的入口进入，作者、课程、分组和讲次关系正确；课程没有进入用户专题。
- Markdown 目录指向存在的源码；网页目录和导航指向实际生成的页面。新增或删除内容后逐项检查，尤其检查 URL 编码、旧地址与路径脚本。
- `npm run build` 和项目验证通过；首页、时间轴、搜索及知识花园仍可找到相应内容。技术检查通过不代表分类判断或知识内容已被证明正确。
- 检查移动端与桌面端的路径可读性，并确认线上实际发布状态；如果受网络或服务延迟影响无法确认，不声称已验证线上效果。
